# Frontend Work To Merge

이 플레이북은 새 작업부터 브랜치·구현·PR·리뷰·머지·재검증을 연결한다. 프로젝트의 기존 정책과 권한을 먼저 확인하고, 이미 승인된 범위에서는 같은 승인을 반복해서 요구하지 않는다. 배포는 머지와 별도 상태다.

## 1. 작업과 기준 확인

기존 티켓이나 감사 문제에 목적·완료 조건·근거를 한 번 기록한다. 작은 수정에 새 ADR이나 문서 묶음을 요구하지 않는다. 새 설계 결정이 실제로 생겼을 때만 기존 ARD/ADR 경로를 사용한다.

```bash
git status --short --branch
git remote -v
git branch --all
```

작업 중인 사용자 변경, 적용 지침, 원격 저장소, 실제 기본 브랜치, develop 사용 여부와 PR 대상 정책을 확인한다. `main`, `master`, `develop` 중 하나를 이름만 보고 추정하지 않는다. 기존 변경을 보존하고 필요하면 격리된 작업 사본을 쓴다.

## 2. 브랜치와 가이드 선택

다음은 가능한 경로이며 프로젝트 정책이 선택한다.

```text
feature → main/master
feature → develop → main/master
```

확인된 기준 브랜치에서 프로젝트 규칙에 맞는 작업 브랜치를 만든다. branch 이름·기준 ref는 실제 작업 값으로 정한 뒤 명령을 실행한다. 기준을 갱신해야 한다면 원격 상태를 먼저 확인하고, 로컬 변경에 영향을 주는 reset을 자동 실행하지 않는다.

가이드는 governance부터 시작하고 [rule routing](../skills/audit-frontend-rules/references/rule-routing.md)으로 필요한 일부만 선택한다. 레이어·CSS 회귀에는 스타일링·테스트를, 포커스와 조작 불가가 있으면 접근성도 선택한다. 저장소에 존재하는 lint·test·build 명령을 사용하며 없는 명령을 성공한 것처럼 쓰지 않는다.

## 3. 구현과 검증

가장 작은 일관된 변경으로 완료 조건을 만족시킨다. 원인·공유 경계·위험이 달라지면 영향을 받는 범위의 계획을 다시 검토한다.

| 위험 | 최소 검증 방향 |
| --- | --- |
| 순수 로직·상태 전이 | 가장 좁은 재현/회귀 테스트 |
| 폼·비동기 UI·오류 복구 | interaction·integration, 필요한 접근성 검증 |
| 인증·권한·결제·파괴적 동작·다중 화면 | 핵심 E2E와 가치 있는 실패 경로 |
| 레이어·공통 CSS | 대표 overlay·breakpoint·긴 콘텐츠·scroll, 실제 클릭/키보드와 화면 확인 |
| 단순 저위험 스타일 수정 | 관련 화면·지원 너비의 집중 수동 확인 또는 기존 visual 검사 |

test 파일·도구 흔적이 있다는 것과 여정이 검증됐다는 것을 구분한다. 실행한 명령, commit, 대상 상태와 결과를 기록한다. 실행하지 못한 browser·기기·backend 경계는 미확인으로 남긴다.

## 4. PR과 코드리뷰

PR에는 문제와 바뀐 동작을 먼저 설명하고 기존 티켓·감사 문제를 연결한다. 최소한 범위, 검증 근거, 남은 쟁점, 필요한 복구 지점을 포함한다. 큰 표를 매번 복제하지 않고 원본 근거를 링크한다.

[코드리뷰 기준](../rules/code-review.md)에 따라 Critical → Standards → Optimization 순서로 검토한다. AI의 동의나 테스트 수를 승인·정상 운영 근거로 대신하지 않는다. 기준 이미지 일괄 갱신, 테스트 삭제, 기대값 완화는 별도 근거 없이 회귀 해결로 처리하지 않는다.

GitHub 종료 키워드(`Closes #123`)는 기본 브랜치 대상 PR에서 처리된다. 기본 브랜치가 main일 때 develop 대상 PR에 이 문구만 적고 이슈 종료를 기대하지 않는다. 개발 브랜치 반영과 최종 완료 조건을 구분하고, PR·브랜치 연결은 확인된 정책대로 유지한다. [공식 동작](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## 5. 머지·재검증·종료

실제 저장소의 필수 check와 리뷰·merge 권한을 확인한다. 이 문서는 그 설정을 강제하거나 현재 설정이 존재한다고 보증하지 않는다. merge는 사용자 요청이나 기존 작업 권한이 그 행위까지 포함할 때 진행한다.

머지된 커밋에서 필요한 검증을 확인하고 문제의 완료 조건에 맞춰 닫는다. 새 경고가 사라졌다는 사실만으로 CSS 결함·취약점·운영 장애가 해결됐다고 확정하지 않는다. 로컬 triage 종료와 GitHub issue 종료, 검증된 수정 완료를 분리한다.

보고할 상태는 필요한 것만 남긴다.

| 상태 | 필요한 근거 |
| --- | --- |
| 구현됨 | 검토 가능한 변경 파일 |
| 검증됨 | 실행한 관련 검사·재현 결과 |
| PR 생성됨 / 머지됨 | 확인된 URL·머지 커밋 |
| 배포됨 | 실제 배포 환경·버전 |
| 효과 확인됨 | 관찰 기간·측정값·해석 |

운영 효과가 늦게 드러나는 작업은 관찰 신호·출처·재검토 조건을 기존 티켓에 남긴다. 자동 점검이 실제로 설정되지 않았다면 예약됐다고 쓰지 않는다.
