# Internationalization Rules

## Purpose

Define how AI agents should handle locale ownership, translated messages, pluralization, formatting, routing, text direction, layout expansion, hydration, and localized SEO without forcing internationalization infrastructure onto projects that do not need it.

## Source Priority

Use the shared precedence in [Rule Governance](./governance.md). Product-supported locales, translation ownership, legal copy, routing policy, content management, and the project's existing i18n library outrank generic message or URL conventions.

## Applicability

- **SHOULD**: Load this rule when a task changes supported locales, user-facing messages, locale routing, language selection, formatting, right-to-left behavior, translation loading, or localized metadata.
- **SHOULD**: Load this rule when hardcoded user-facing text conflicts with an established multi-locale architecture.
- **SHOULD**: Do not load this rule for every text edit in a confirmed single-locale product unless localization readiness is an explicit requirement.

## Locale Ownership

- **MUST**: Identify the supported locale set, default locale, locale source, fallback behavior, and owner before changing locale-sensitive behavior.
- **MUST**: Validate URL, cookie, header, storage, profile, and API locale values against the supported locale set.
- **SHOULD**: Define precedence among URL locale, explicit user choice, stored preference, account setting, and request-language negotiation.
- **SHOULD**: Let the router own locale when locale is part of the public URL contract; use [State Ownership Rules](./state-ownership.md) for other preference and persistence decisions.
- **MUST**: Keep server-rendered and first client-rendered locale, messages, time zone, and formatting inputs compatible to avoid hydration mismatches.
- **SHOULD**: Preserve the current route, query, and user intent when switching locale according to product policy.
- **MUST**: Do not infer a user's legal region, currency, consent policy, or authorization from language preference alone.

## Message Ownership

- **SHOULD**: Reuse the project's existing message catalog, namespace, extraction, and translation workflow.
- **SHOULD**: Keep message keys stable and based on owned meaning or project convention rather than component file location alone.
- **MUST**: Do not build translated sentences by concatenating fragments whose order or grammar can vary by locale.
- **SHOULD**: Use named placeholders and full messages so translators can reorder values and preserve context.
- **MUST**: Keep placeholders, markup expectations, and variable types compatible across locale variants.
- **SHOULD**: Define missing-message behavior for development and production without silently displaying misleading copy.
- **MUST**: Do not render translator-controlled HTML without the approved rich-content trust and sanitization boundary.
- **SHOULD**: Keep authorization, validation codes, and business decisions language-neutral; translate the user-facing presentation separately.

## Pluralization And Formatting

- **MUST**: Use the existing i18n library or platform `Intl` APIs for plural categories, dates, times, numbers, currency, units, lists, and relative time when locale changes their representation.
- **MUST**: Do not implement pluralization with English-only `count === 1` logic in a multi-locale path.
- **SHOULD**: Make time zone, calendar, numbering system, and currency inputs explicit when product correctness depends on them.
- **MUST**: Do not infer currency from locale when the transaction or account owns the currency.
- **SHOULD**: Keep machine-readable values separate from localized display strings.
- **SHOULD**: Reuse formatter instances or the existing formatting abstraction where repeated construction has measured cost, without creating speculative caches.
- **SHOULD**: Test boundary values that change plural category, date, day, or currency display for supported representative locales when formatting affects important user decisions or repeated correctness risk.

## Language And Direction

- **MUST**: Set the document language with the appropriate `lang` value and update it when the rendered document locale changes.
- **MUST**: Set text direction explicitly when required; do not assume direction can always be derived from language.
- **SHOULD**: Use `dir="auto"`, `bdi`, or an established equivalent for user-generated or unknown-direction text where mixed direction can corrupt layout.
- **SHOULD**: Prefer CSS logical properties and direction-aware assets for components that support both left-to-right and right-to-left rendering.
- **MUST**: Preserve semantic order, keyboard order, and icon meaning when mirroring layouts.
- **SHOULD**: Verify font coverage, line breaking, truncation, form controls, and fallback fonts for the supported scripts.

## Layout And Content Expansion

- **MUST**: Allow user-facing text to expand without overlapping, clipping, hiding required actions, or relying on fixed English-length containers.
- **SHOULD**: Avoid using translated text as a stable programmatic identifier, test selector, analytics key, or persistence key.
- **SHOULD**: Keep truncation intentional and provide access to essential full content.
- **SHOULD**: Test a long-message locale or approved pseudo-localization path when shared compact UI has material expansion risk.
- **MUST**: Keep accessible names, validation messages, live-region announcements, and error recovery localized with the visible workflow.

## Next.js And SEO Boundaries

- **MUST**: Identify App Router, Pages Router, or mixed routing before applying locale route conventions.
- **SHOULD**: App Router: follow the installed Next.js internationalization pattern and keep dictionaries server-side when client access is unnecessary.
- **SHOULD**: Pages Router: follow configured `i18n`, domain, subpath, router locale, and data-fetching conventions without introducing App Router file patterns.
- **MUST**: Do not mix locale URL strategies across route trees without a migration and redirect contract.
- **SHOULD**: For indexable localized pages, align canonical URLs, `hreflang`, status codes, redirects, internal links, and sitemap entries using [SEO Rules](./seo.md).
- **MUST**: Do not claim search-engine language targeting from translation files alone; verify rendered URL and metadata signals.

## Testing

- **SHOULD**: Unit-test message parameters, formatter boundaries, locale validation, and fallback selection when they contain meaningful logic.
- **SHOULD**: Use component or integration tests for message rendering, text expansion, direction, locale switching, and hydration-sensitive behavior.
- **SHOULD**: Test zero, one, multiple, and locale-specific plural categories where the message supports them.
- **SHOULD**: Test representative time zones and date boundaries when time-sensitive behavior affects user decisions.
- **SHOULD**: Reserve localized E2E coverage for critical journeys, locale routing, payment or legal copy, and cross-boundary failures that lower layers cannot represent.
- **SHOULD**: Prefer stable semantic selectors over translated text when tests must run across multiple locales.

## Avoid Over-engineering

- **MUST**: Do not add an i18n dependency, locale router, extraction pipeline, or translation service to a single-locale project without an approved product requirement.
- **SHOULD**: Do not replace an established message library during an unrelated copy change.
- **SHOULD**: Do not move internal logs, developer-only errors, protocol values, or stable identifiers into translation catalogs without user-facing value.
- **SHOULD**: Avoid loading every locale's messages into the client when the existing framework can select them by route or server boundary.
- **SHOULD**: Record missing product decisions instead of inventing supported locales, fallback copy, legal translations, or URL policy.

## Verification

Report:

- Supported locales, default, source, fallback, and routing ownership
- Message catalogs, keys, placeholders, and formatters changed
- Language, direction, layout expansion, font, and accessibility behavior verified
- Server-client locale and hydration behavior
- Localized URL, canonical, `hreflang`, redirect, and sitemap checks when applicable
- Unit, component, integration, and E2E checks run
- Unverified translations, regional policy, time zones, or content ownership

Do not claim internationalization completeness from one translated screen. Verify the locale lifecycle and representative user journeys.

## AI Agent Checklist

- Did I confirm supported locales and locale precedence?
- Are locale inputs validated and server-client values compatible?
- Are messages complete units with reorderable placeholders?
- Are plural, date, time, number, unit, and currency rules locale-aware?
- Are document language and text direction correct?
- Can translated text expand without breaking the layout?
- Are localized URL and SEO signals coherent where applicable?
- Did I reuse the existing i18n stack without broadening product scope?
