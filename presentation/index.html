Frontend Agent Playbook

AI가 코드를 작성해도
시스템의 통제권은 유지하도록

검색 가능한 프론트엔드 지식을 더 모으기보다, 웹 시스템을 어떻게 이해하고 진단하고 변경하고 검증할지 판단 모델·규칙·스킬·증거로 연결한 플레이북입니다.

증상 → 시스템 경계 근거 → 판단 → 검증 유지 · 개선 · 제안 · 거절

01 · Problem

지식은 충분했지만, 판단과 소유권은 자동으로 생기지 않았습니다

AI는 기존 코드와 관례를 참고합니다. 나쁜 패턴이 쌓일수록 그 패턴을 정상적인 방식으로 받아들여 반복할 가능성도 커집니다.

공식 문서는 빠르게 찾을 수 있어도 왜 느린지, 어디서 상태가 어긋났는지, 생성된 변경을 받아도 되는지는 시스템 경계와 실제 근거를 따라 판단해야 했습니다.

01
증상과 원인이 쉽게 섞임느림, stale state, hydration 오류 같은 증상은 Network·Server·Rendering·JS와 데이터 흐름 중 실제 실패 경계를 찾아야 합니다.
02
나쁜 코드가 다음 기준이 됨임시 처리와 일관성 없는 구조가 누적되면 AI도 이를 기존 관례로 받아들여 같은 문제를 반복할 수 있습니다.
03
생성된 코드가 설명 없이 남음코드가 동작해도 데이터 흐름, 실패 방식과 복구 지점을 이해하지 못하면 시스템 소유권은 약해집니다.

02 · Workflow

판단 모델·규칙·스킬·증거를 하나의 실행 흐름으로 묶었습니다

01 · JUDGMENT어떻게
판단할지증상에서 시스템 경계와 확인할 근거를 좁히는 사고 과정
02 · RULES어떤 제약을
지킬지프로젝트와 버전에 맞는 좁고 검증 가능한 제약
03 · SKILLS어떻게
실행할지탐색부터 제안·승인·적용·검증까지 반복 가능한 절차
04 · EVIDENCE무엇으로
확인할지Analyzer, 코드, 런타임과 테스트에서 얻은 근거를 구분
유지 · 이미 좋은 패턴은 훼손하지 않도록 지킴 개선 · 현재 작업 범위에서 검증 가능한 만큼 개선 제안 · 범위 밖 위험은 근거와 완료 기준을 갖춘 초안으로 남김 거절 · 근거·범위·검증이 부족한 변경은 수용하지 않음

04 · Boundaries

자동화는 검토 대상을 찾고, 최종 결정은 사람이 내립니다

자동 분석

먼저 살펴볼 항목

  • 버전과 Router 구성
  • HTML 콘텐츠의 출처·정제 여부와 테스트 공백
  • 근거가 충분한지와 먼저 볼 순서
  • 민감 정보가 제거된 검토 보고서
사람의 확인

사람이 확인

  • 입력 데이터의 실제 출처와 신뢰 경계
  • 사용자·비즈니스에 미치는 실제 영향
  • 기존 방어 로직과 예외가 타당한지
  • 유지·개선·제안·거절 중 처리 방향
  • 수정과 이슈 등록의 우선순위·시점
자동화하지 않음

자동으로 결정하지 않음

  • 정적 패턴만으로 취약점 확정
  • 삭제 후보의 자동 제거
  • 점수를 품질 보증이나 배포 승인에 사용
  • 승인 없는 규칙 적용·파일 수정·이슈 등록

현재 상태: 안정 버전은 v0.1.1이며 분석기 v0.2와 초기 판단 모델은 main에서 검증 중입니다. 정적 패턴 검사와 판단 모델 모두 실제 프로젝트에서 유효했던 결정과 노이즈를 더 측정해야 합니다.
