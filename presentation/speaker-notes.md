# Frontend Agent Playbook 발표자 노트

목표 시간은 11~12분이다. 기능을 모두 설명하기보다 문제 정의, 실행 구조, 한계, 다음 검증 순서만 전달한다. 남는 2~3분은 질문과 반응을 받는 데 사용한다.

## 1. 소개 — 약 1분

### 반드시 말할 내용

Claude나 Codex를 실제 작업에 사용하면서, AI가 코드를 만드는 속도보다 내가 시스템을 계속 이해하고 통제할 수 있는지가 더 신경 쓰였다.

React, Next.js, TypeScript 공식 문서는 AI가 빠르게 찾을 수 있다. 하지만 왜 느린지, 어디서 데이터가 어긋났는지, 생성된 변경을 받아도 되는지는 여전히 시스템 경계와 실제 근거를 따라 판단해야 한다.

그래서 검색 가능한 지식을 더 모으기보다 진단, 판단, 검증과 소유권 전달을 반복 가능한 흐름으로 만드는 플레이북으로 방향을 잡았다.

### 오프닝 예시

> Claude나 Codex를 실제 작업에 쓰면서, AI가 코드를 만드는 속도보다 제가 시스템을 계속 이해하고 통제할 수 있는지가 더 신경 쓰였습니다. 공식 문서는 빠르게 찾을 수 있지만 왜 느린지, 어디서 상태가 어긋났는지, 생성된 변경을 받아도 되는지는 별도의 판단이 필요했습니다. 그래서 판단 모델, 규칙, 스킬과 증거를 하나의 플레이북으로 연결해봤습니다.

## 2. 문제와 이유 — 약 2분

### 반드시 말할 내용

첫째, 증상과 원인을 구분해야 한다. 느린 화면이나 stale state를 보고 바로 memoization이나 Effect 수정부터 하면 실제 Network, Server, Rendering, JS 또는 데이터 소유권 문제를 놓칠 수 있다.

둘째, AI는 기존 코드와 관례를 참고한다. 임시 처리와 나쁜 패턴이 누적되면 AI도 이를 정상적인 프로젝트 관례로 반복할 수 있다.

셋째, 생성된 코드가 동작하는 것만으로는 부족하다. 엔지니어가 데이터 흐름, 실패 방식, 검증과 복구 지점을 설명할 수 있어야 시스템 소유권이 유지된다.

### 연결 문장

> 그래서 목표를 지식을 많이 주는 것으로 잡지 않고, 증상에서 시스템 경계와 근거를 좁힌 뒤 유지·개선·제안·거절로 연결하는 것으로 잡았습니다.

## 3. 동작 구조 — 약 2분 20초

### 네 요소 구분

- Judgment는 증상에서 어떤 시스템 경계와 근거를 확인할지 정의한다.
- Rules는 프로젝트와 버전에 맞는 좁은 제약을 제공한다.
- Skills는 코드베이스를 어떻게 탐색하고 제안하고 승인받아 적용할지 정의한다.
- Evidence는 Analyzer, 코드, 런타임과 테스트에서 얻은 사실과 추론을 구분한다.

Analyzer가 최종 판단자가 아니라는 점을 강조한다. 정적 패턴은 출발점이며 실제 영향과 우선순위는 코드, 런타임, 담당자의 확인이 필요하다.

코드 변경의 결과는 네 방향으로 분류한다.

- 유지: 이미 좋은 패턴을 훼손하지 않는다.
- 개선: 현재 작업 범위에서 검증 가능한 만큼 개선한다.
- 제안: 범위 밖 위험은 근거, 영향, 완료 기준을 갖춘 이슈 초안으로 제안한다.
- 거절: 근거, 범위 또는 검증이 부족한 변경은 수용하지 않는다.

이 분류는 코드 변경에 대한 처리 방향이다. 규칙과 스킬 자체의 적용 여부를 기록하는 Keep, Conditional, Disable, Removal candidate와는 별도 축이다.

수정과 외부 이슈 등록은 각각 별도 승인을 받아야 한다.

## 4. 데모 — 약 3분

데모에서는 여러 분석 항목을 빠르게 넘기지 말고 한 흐름만 보여준다.

1. 프로젝트 폴더와 검색 노출 범위를 선택한다.
2. 내부 전용 프로젝트에서는 SEO 검사가 필수가 아닌 선택 사항으로 바뀌는 것을 보여준다.
3. HTML 직접 삽입 코드가 곧바로 XSS로 확정되지 않고, 콘텐츠 출처와 서버 정제 여부를 먼저 확인해야 하는 항목으로 나타나는 것을 보여준다.
4. 항목 ID, 근거, 문제가 아닐 수 있는 근거, 확인하지 못한 정보가 Markdown 검토 보고서에 남는 것을 보여준다.
5. 대시보드가 파일을 수정하거나 이슈를 등록하는 것이 아니라 코드베이스 점검 스킬의 다음 판단으로 넘긴다는 점을 설명한다.

### 데모 중 사용할 문장

> 여기서 중요한 것은 많이 발견했다는 사실보다 왜 위험할 수 있는지, 무엇이 아직 확인되지 않았는지, 다음에 무엇을 검증해야 하는지가 같이 나온다는 점입니다.

> 이 결과는 수정 명령이 아닙니다. 코드베이스 점검 스킬이 저장소 맥락을 다시 확인하고 유지·개선·이슈 제안 중 하나를 판단하기 위한 검토 자료입니다.

데모가 지연되면 실제 실행을 반복하지 말고 슬라이드의 캡처 화면으로 설명한다.

## 5. 현재 한계 — 약 1분 10초

완성된 보안 분석기나 품질 보증 도구로 소개하지 않는다.

- 현재 분석은 정적 휴리스틱 중심이다.
- 미발견은 안전을 의미하지 않는다.
- 점수는 배포 승인 기준이 아니다.
- 데드코드는 삭제 후보만 제시하고 자동 삭제하지 않는다.
- 실제로 도움이 된 지적과 오탐의 비율을 보여줄 데이터가 아직 부족하다.

### 설명 문장

> 자동화는 후보와 근거를 정리하는 역할까지만 맡기고, 실제 영향과 행동 결정은 사람의 확인과 승인에 남겨뒀습니다.

## 6. 다음 계획과 질문 — 약 2분

다음 우선순위는 규칙 추가가 아니라 판단 모델의 실전 검증이다.

1. 성능 저하, 재현하기 어려운 버그, 중요한 AI 생성 변경에 초기 판단 모델을 적용한다.
2. 판단이 유지, 개선, 제안, 거절 중 어디로 이어졌는지와 노이즈를 기록한다.
3. 기준선과 변경 비교를 활용해 반복 분석 노이즈를 줄인다.
4. 기존 규칙을 핵심 제약, 버전 어댑터, 도메인 가이드, 통합 대상과 삭제 후보로 재분류한다.

### 피드백 요청

> AI가 코드를 작성한 뒤 시스템 이해가 가장 자주 끊기는 지점이 어디인지 궁금합니다.

> 유지·개선·제안·거절로 나누는 흐름이 실제 업무에서 도움이 될지도 의견을 듣고 싶습니다.

### 마무리 예시

> 이걸 완성된 분석 도구로 소개하려는 것은 아닙니다. AI가 코드를 작성해도 엔지니어가 시스템 경계와 근거를 이해하고, 사람의 승인 아래 다음 행동으로 연결할 수 있는지 실험한 결과물입니다. 괜찮게 보셨다면 마지막 승인 게이트로 GitHub Star도 한 번 부탁드립니다.

## 시간이 부족할 때

- 2번 슬라이드의 세 사례는 제목만 말하고 세부 예시는 하나만 설명한다.
- 3번 슬라이드는 네 요소 정의와 유지·개선·제안·거절만 말한다.
- 데모는 내부 전용 SEO 사례 하나만 보여준다.
- 로드맵 네 항목 중 실제 프로젝트 검증과 오탐 측정만 말한다.
