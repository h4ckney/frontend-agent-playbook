# Frontend Agent Playbook 발표자 노트

목표 시간은 11~12분이다. 기능을 모두 설명하기보다 문제 정의, 실행 구조, 한계, 다음 검증 순서만 전달한다. 남는 2~3분은 질문과 반응을 받는 데 사용한다.

## 1. 소개 — 약 1분

### 반드시 말할 내용

Claude나 Codex를 실제 작업에 사용하면서, AI가 코드를 아예 못 만드는 문제보다 프로젝트 맥락을 놓치는 문제가 더 신경 쓰였다.

React, Next.js, TypeScript에는 이미 좋은 공식 가이드가 많다. 하지만 가이드가 생태계별로 흩어져 있고, 현재 프로젝트의 버전과 구조에 맞게 무엇을 선택하고 검증할지는 별도의 판단으로 남는다.

그래서 새로운 best practice를 발명하기보다 기존 근거를 프로젝트 맥락에 맞게 선택하고, 승인 아래 다음 행동으로 연결하는 플레이북을 만들어봤다.

### 오프닝 예시

> Claude나 Codex를 실제 작업에 쓰면서, AI가 코드를 못 만드는 것보다 프로젝트 맥락을 놓치는 문제가 더 신경 쓰였습니다. 좋은 공식 가이드는 이미 많지만, 현재 코드베이스에 어떤 규칙을 적용할지 선택하고 검증하는 흐름은 흩어져 있었습니다. 그래서 규칙, 스킬, 분석과 승인을 하나의 플레이북으로 연결해봤습니다.

## 2. 문제와 이유 — 약 2분

### 반드시 말할 내용

첫째, 같은 Next.js라도 Pages Router와 App Router의 권고가 다르고 React 버전과 RSC 사용 여부도 별개다. 좋은 규칙도 잘못된 맥락에 적용하면 회귀나 불필요한 작업이 된다.

둘째, AI는 기존 코드와 관례를 참고한다. 임시 처리와 나쁜 패턴이 누적되면 AI도 이를 정상적인 프로젝트 관례로 반복할 수 있다.

셋째, 문제를 많이 찾는 것만으로는 부족하다. 지금 지킬 패턴, 현재 범위에서 개선할 문제, 당장 처리하지 않고 이슈로 제안할 문제를 나눠야 실제 행동으로 이어진다.

### 연결 문장

> 그래서 목표를 규칙을 많이 주는 것으로 잡지 않고, 현재 프로젝트에 맞는 규칙만 선택해 유지·개선·제안으로 연결하는 것으로 잡았습니다.

## 3. 동작 구조 — 약 2분 20초

### 네 요소 구분

- Rules는 무엇을 고려할지 정의한다.
- Skills는 코드베이스를 어떻게 탐색하고 판단하고 적용할지 정의한다.
- Analyzer는 먼저 살펴볼 분석 항목과 근거 수준을 제공한다.
- Playbook은 이 셋을 프로젝트 맥락, 승인, 검증, 결정 기록으로 연결한다.

Analyzer가 최종 판단자가 아니라는 점을 강조한다. 정적 패턴은 출발점이며 실제 영향과 우선순위는 코드, 런타임, 담당자의 확인이 필요하다.

결과는 세 방향으로 분류한다.

- 유지: 이미 좋은 패턴을 훼손하지 않는다.
- 개선: 현재 작업 범위에서 검증 가능한 만큼 개선한다.
- 제안: 범위 밖 위험은 근거, 영향, 완료 기준을 갖춘 이슈 초안으로 제안한다.

수정과 외부 이슈 등록은 각각 별도 승인을 받아야 한다.

## 4. 데모 — 약 3분

데모에서는 여러 분석 항목을 빠르게 넘기지 말고 한 흐름만 보여준다.

1. 프로젝트 폴더와 검색 노출 범위를 선택한다.
2. 내부 전용 프로젝트에서는 SEO 검사가 필수가 아닌 선택 사항으로 바뀌는 것을 보여준다.
3. HTML 직접 삽입 코드가 곧바로 XSS로 확정되지 않고, 콘텐츠 출처와 서버 정제 여부를 먼저 확인해야 하는 항목으로 나타나는 것을 보여준다.
4. 항목 ID, 근거, 문제가 아닐 수 있는 근거, 확인하지 못한 정보가 Markdown 검토 보고서에 남는 것을 보여준다.
5. 대시보드가 파일을 수정하거나 이슈를 등록하는 것이 아니라 코드베이스 점검 스킬의 다음 판단으로 넘긴다는 점을 설명한다.

### 데모 중 사용할 문장

> 여기서 중요한 것은 많이 발견했다는 사실보다 왜 위험할 수 있는지, 무엇이 아직 확인되지 않았는지, 다음에 무엇을 검증해야 하는지가 같이 나온다는 점입니다.

> 이 결과는 수정 명령이 아닙니다. 코드베이스 점검 스킬이 저장소 맥락을 다시 확인하고 유지·개선·이슈 제안 중 하나를 판단하기 위한 검토 자료입니다.

데모가 지연되면 실제 실행을 반복하지 말고 슬라이드의 캡처 화면으로 설명한다.

## 5. 현재 한계 — 약 1분 10초

완성된 보안 분석기나 품질 보증 도구로 소개하지 않는다.

- 현재 분석은 정적 휴리스틱 중심이다.
- 미발견은 안전을 의미하지 않는다.
- 점수는 배포 승인 기준이 아니다.
- 데드코드는 삭제 후보만 제시하고 자동 삭제하지 않는다.
- 실제로 도움이 된 지적과 오탐의 비율을 보여줄 데이터가 아직 부족하다.

### 설명 문장

> 자동화는 후보와 근거를 정리하는 역할까지만 맡기고, 실제 영향과 행동 결정은 사람의 확인과 승인에 남겨뒀습니다.

## 6. 다음 계획과 질문 — 약 2분

다음 우선순위는 규칙 추가가 아니라 실전 검증이다.

1. Pages Router, App Router, 혼합 구조의 실제 프로젝트에서 검증한다.
2. 분석 항목이 유지, 수정, 이슈, 제외 중 어디로 이어졌는지 기록한다.
3. 기준선과 변경 비교를 활용해 반복 분석 노이즈를 줄인다.
4. 페이지별 메타데이터처럼 현재 얕은 Next.js 분석은 파서 기반 분석이 실제로 정확도를 높이는지 먼저 측정한다.

### 피드백 요청

> AI 코드리뷰에서 가장 자주 겪는 잘못된 지적이나 과도한 권고가 무엇인지 궁금합니다.

> 유지·즉시 개선·후속 이슈로 나누는 흐름이 실제 업무에서 도움이 될지도 의견을 듣고 싶습니다.

### 마무리 예시

> 이걸 완성된 분석 도구로 소개하려는 것은 아닙니다. AI가 프로젝트에 맞는 규칙을 선택하고, 근거를 확인하고, 사람의 승인 아래 다음 행동으로 연결할 수 있는지 실험한 결과물입니다. 괜찮게 보셨다면 마지막 승인 게이트로 GitHub Star도 한 번 부탁드립니다.

## 시간이 부족할 때

- 2번 슬라이드의 세 사례는 제목만 말하고 세부 예시는 하나만 설명한다.
- 3번 슬라이드는 네 요소 정의와 유지·개선·제안만 말한다.
- 데모는 내부 전용 SEO 사례 하나만 보여준다.
- 로드맵 네 항목 중 실제 프로젝트 검증과 오탐 측정만 말한다.
