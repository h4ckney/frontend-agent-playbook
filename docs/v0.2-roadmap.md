## 1. 배경

### 기준 코드베이스

- Next.js 13 Pages Router 전용, RSC 미사용
- React 18, `satisfies`를 지원하는 TypeScript 4.x
- 검증된 서버 상태 도구와 class 기반 DI 및 observable client state 조합
- 성숙한 unit test suite와 상대적으로 작은 Playwright E2E suite
- 기존 오류 모니터링 및 성숙한 CI 운영

### 실제 감사에서 확인된 결과

- 여러 feature에서 `dangerouslySetInnerHTML` 사용이 발견되었으나 DOMPurify 등 sanitizer 의존성과 import는 발견되지 않았다.
- 일부 HTML은 백엔드 콘텐츠로 추정되지만 제3자 광고와 사용자 유래 가능 콘텐츠도 포함되어 신뢰경계가 불명확하다.
- 인증 토큰과 비밀번호를 localStorage 또는 sessionStorage에 직접 저장한 사례는 없었다.
- 제3자 client SDK의 공개 환경변수 값은 설계상 공개 식별자이므로 비밀정보 노출로 분류하지 않았다.
- E2E가 일부 저위험 여정에 편중되어 제출, 결제, 회원가입 완주 같은 고위험 전환 여정이 비어 있었다.
- react-hooks/exhaustive-deps가 꺼져 있고 dependency 누락 관련 버그 이력이 확인되어 이 코드베이스에서는 경고 승격 권고가 정당화되었다.

### v0.1 평가

강점:

- 사용자 요구, 기존 코드베이스, 버전별 공식 문서를 저장소의 일반 규칙보다 우선한다.
- Next.js router와 React RSC 지원을 major version만으로 추론하지 않는다.
- 긴급 권고를 억지로 세 개 채우지 않고 Effect dependency 선호를 근거 없이 강제하지 않는다.
- 문서 검증 스크립트가 있고 성숙도를 과장하지 않는다.

약점:

- MUST, SHOULD, MAY 체계가 전체 규칙에 일관되게 적용되지 않았다.
- 모든 문서를 한 번에 주입하는 사용 방식은 컨텍스트 비용이 크다.
- 정규식 기반 대시보드 점수가 실제 보안 보증처럼 해석될 수 있다.
- audit 스킬의 실제 코드베이스 forward-test 결과가 없다.
- LICENSE와 CI 연결이 없어 외부 팀의 복사 채택을 막는다.
- 일부 예시는 production-grade 기준에 비해 단순하다.

## 2. 실행 원칙

1. 잘못된 확신을 제거한 뒤 기능을 확장한다.
2. 정적 탐지 결과와 취약점 확정을 구분한다.
3. framework, router, rendering model, lint 설정과 실제 버그 이력을 먼저 확인한다.
4. 자동화 가능한 규칙과 사람 또는 에이전트 판단이 필요한 규칙을 분리한다.
5. 새 규칙은 실제 감사에서 반복된 문제를 근거로 추가한다.
6. 긴급 권고는 최대 세 개이며 시급한 문제가 적으면 목록을 채우지 않는다.

## 3. P0: 대시보드 안전장치

현재 대시보드는 휴리스틱 결과를 지나치게 확정적으로 보이게 만들 수 있으므로 공개 사용 확대 전에 수정한다.

### 자동 판정 범위 제한

결과를 다음 증거 수준으로 구분한다.

- **관찰된 사실**: 파일과 설정에서 직접 확인된 패턴
- **위험 추론**: 관찰된 사실로부터 검토가 필요하다고 판단한 내용
- **정보 부족**: 백엔드 정제, 런타임 동작, 배포 설정 등 정적 분석으로 확인할 수 없는 내용
- **삭제 후보**: 참조와 부작용 검증이 필요한 dead-code 후보

정적 문자열 탐지만으로 XSS 취약점, 안전성, 미사용 코드 또는 삭제 가능성을 확정하지 않는다. Dead code는 자동 삭제하지 않으며 삭제 승인을 의미하지 않는다.

### 점수 해석 제한

- 숫자 점수를 제거하거나 보조 지표로 낮추고 결과의 신뢰도를 별도로 표시한다.
- Critical 0건을 안전 판정처럼 표시하지 않는다.
- 동일 원인에서 발생한 여러 파일은 하나의 finding으로 묶는다.
- 파일 수에 따라 감점이 계속 누적되지 않도록 상한을 둔다.
- 품질 보증, 보안 인증 또는 배포 승인에 사용할 수 없음을 화면과 Markdown 보고서에 표시한다.

고정 안내 문구:

> 이 결과는 정적 휴리스틱입니다. 미발견은 안전을 의미하지 않으며 품질 보증, 보안 인증 또는 배포 승인에 사용할 수 없습니다.

### 분석 입력 제한

- node_modules, .git, .next, dist, build, coverage, vendor 및 생성 코드를 제외한다.
- 바이너리와 대용량 파일을 제외한다.
- .env 실제 값과 secret, token, 개인정보를 읽거나 보고서에 기록하지 않는다.
- 근거에는 필요한 최소 경로와 패턴 종류만 표시한다.
- 분석은 브라우저 로컬에서 수행하며 외부 전송을 추가하지 않는다.

### 탐지 개선

- HTML sink 사용과 sanitizer 의존성 및 import 부재를 교차 검사한다.
- dangerouslySetInnerHTML 개수, sanitizer 발견 여부, 신뢰경계 문서 존재 여부를 각각 표시한다.
- 리터럴 변수명만으로 token 저장을 판단하지 않고 wrapper와 상수에 따른 구조적 미탐 가능성을 표시한다.
- 심층 audit 보고서와 대시보드 휴리스틱 결과의 제목 및 증거 수준을 구분한다.

### P0 Exit

- 기준 코드베이스에서 여러 HTML sink와 sanitizer 미발견이 최우선 검토 항목으로 출력된다.
- 결과가 XSS 취약점을 확정하지 않고 신뢰경계와 정제 여부를 추가 확인하도록 안내한다.
- dead-code finding은 항상 후보로 표시되며 자동 삭제 기능이 없다.
- 민감한 환경변수 값이 화면, 로그, 다운로드 보고서에 포함되지 않는다.
- 숫자 점수만으로 안전 또는 배포 가능 상태를 판단할 수 없다.

## 4. P1: v0.2 채택 기반

### LICENSE

- 기본 선택은 MIT License로 한다.
- README의 복사 및 적용 안내와 라이선스 조건이 충돌하지 않는지 확인한다.

Exit: 루트에 유효한 LICENSE가 있고 외부 사용자가 사용, 수정, 배포 조건을 확인할 수 있다.

### 문서 검증 CI

- GitHub Actions에서 node scripts/validate-docs.mjs를 실행한다.
- pull request와 main push에서 실행한다.
- 별도 의존성 설치가 필요 없는 현재 검증 방식을 유지한다.

Exit: 모든 PR에서 Markdown 링크, 필수 섹션, skill metadata 검증이 자동 실행된다.

### 규칙 수준 태깅

모든 실행 가능한 규칙 항목에 다음 수준을 적용한다.

- **MUST**: 보안, 접근성, 데이터 무결성, 명백한 정확성 요구
- **SHOULD**: 일반적으로 따르되 프로젝트 근거가 있으면 예외 가능
- **MAY**: 선택적 개선 또는 프로젝트 선호

단순 설명, 목적, 참고 링크에는 억지로 수준을 붙이지 않는다. 예외에는 이유, 적용 범위와 검증 방법을 기록한다.

Exit:

- 모든 실행 가능한 rule statement가 수준을 가진다.
- validate-docs.mjs가 수준 없는 새 rule statement를 탐지한다.
- MUST와 SHOULD의 예외 처리 방식이 governance에 명시된다.

## 5. P1: Audit Skill Forward-Test

최소 두 개, 권장 세 개의 실제 또는 대표 코드베이스에서 실행한다.

1. Pages Router 전용
2. App Router 전용
3. Mixed Router

보고서 필수 내용:

- framework, router, React, TypeScript 버전
- RSC, SSR, CSR 구분
- 기존 lint, test, CI, observability 도구
- 적용한 규칙과 제외한 규칙 및 이유
- 관찰된 사실과 추론의 구분
- 최대 세 개의 긴급 권고
- unit, component, integration, E2E 공백
- security, SEO, dead-code 후보
- over-engineering 방지 결정

Pages Router 보고서에는 다음 결정을 포함한다.

- App Router와 RSC 규칙 제외
- 공개 client key를 secret 위반으로 오탐하지 않음
- UI 상태용 browser storage를 token 저장 위반으로 오탐하지 않음
- exhaustive-deps 권고는 비활성 설정과 실제 버그 이력을 함께 근거로 사용
- E2E 개수가 아니라 고위험 전환 여정 공백을 기준으로 우선순위 결정

Exit: examples/audits에 재현 가능한 실제 감사 보고서가 두 개 이상 존재한다.

## 6. P2: 컨텍스트 경제와 규칙 라우팅

governance만 기본으로 로드하고 작업 유형과 코드베이스 특성에 따라 필요한 규칙만 선택한다.

- React component: governance, React, TypeScript, accessibility, testing
- Next.js metadata 또는 route: governance, 해당 router의 Next.js 규칙, SEO
- Data mutation: governance, data fetching/cache, error handling, testing
- Security review: governance, security/privacy, code review
- Dead-code removal: governance, dead code, testing, code review

각 skill에는 trigger, applicable framework/router, required evidence, output format을 기계 판독 가능한 형태로 기록한다. 모든 룰을 한 번에 주입하는 방식을 기본 사용법으로 권장하지 않는다.

Exit:

- 작업 유형별 rule routing 문서가 있다.
- 대표 작업에서 전체 문서 대신 필요한 subset만 선택할 수 있다.
- router와 RSC 조건이 routing 단계에서 판별된다.

## 7. P2: 규칙과 강제 도구 매핑

ESLint, TypeScript, framework config 또는 CI로 확실히 강제할 수 있는 규칙을 자동화 레이어로 옮긴다.

매핑 표 항목:

- rule statement와 level
- 적용 가능한 도구와 권장 설정
- version 조건
- false-positive 위험
- 자동화 불가능한 수동 검토

제약:

- 새 lint plugin은 기존 프로젝트에 있거나 반복 위험을 해결할 때만 권장한다.
- react-hooks/exhaustive-deps는 무조건 켜지 않는다. 활성 lint 정책 또는 실제 synchronization bug 근거가 있을 때 권고한다.
- no-explicit-any처럼 예외가 필요한 규칙은 blanket ban으로 표현하지 않는다.

Exit: React, TypeScript, accessibility, security 영역의 강제 가능 규칙에 대한 매핑 표와 적용 예시가 있다.

## 9. P3: 반복 증거 기반 규칙 확장

다음은 현재 후보 순서다. 반복 증거, 명확한 production risk 또는 사용자가 승인한 범위가 달라지면 순서를 갱신하고 이유를 기록한다.

1. 폼 및 schema validation: client UX validation과 server enforcement 구분
2. 상태관리: server, client, global state의 소유권
3. 디자인 시스템 및 styling: token, variant, accessibility, escape hatch
4. i18n: message key, pluralization, formatting, layout expansion
5. bundle 및 dependency budget

모든 영역을 한 번에 추가하지 않는다. 실제 감사에서 두 번 이상 반복되거나 명확한 production risk가 확인된 항목부터 작성한다.

Progress: 폼 및 runtime validation은 사용자 승인과 runtime trust-boundary failure가 correctness, security, data integrity에 미치는 명확한 production risk에 따라 먼저 추가했다. 규칙은 trust boundary, client UX와 server authority, schema 재사용, 접근성, 개인정보 보호, 위험 기반 테스트를 포함한다. 상태 소유권은 다음 우선 후보로 유지한다.

## 12. v0.2 Release Gate

다음 조건을 모두 만족해야 v0.2로 표시한다.

- LICENSE가 존재한다.
- 문서 검증이 CI에서 실행된다.
- 실행 가능한 규칙 항목에 MUST, SHOULD, MAY 수준이 적용된다.
- 대시보드가 미탐을 안전으로 표현하지 않는다.
- 대시보드 입력과 보고서에서 민감정보가 보호된다.
- 실제 코드베이스 audit 보고서가 두 개 이상 존재한다.
- README가 전체 문서 주입 대신 필요한 rule subset 사용을 안내한다.
- 알려진 제한과 수동 검증 범위가 문서화되어 있다.
- 공개 branch와 release tag의 reachable history에 pre-generalization stack 및 audit-detail fingerprint가 남아 있지 않다.
